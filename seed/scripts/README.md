# scripts/

Support tooling for the walkthrough. Everything here runs manually (or in CI, for checkpoints); nothing is wired into a build step.

**No subfolders: the name prefix is the taxonomy.** `cluster-*` is lifecycle, `checkpoint-NN` is a stage gate, `check-*` is an environment pin, `act-N-drill` is a drill runner, `*-time` scripts each measure one number from artifacts (`rung-time`: how fast a good change lands; `detect-time`: how fast a bad one surfaces), and `*-gate` scripts are **evidence gates**: `slo-gate` (performance: did the rung below earn promotion), `policy-gate` (standards: does the render obey policy/), `style-gate` (style: does the YAML obey the convention, via `.yamllint.yaml`). Prefixes keep the walkthrough's `./scripts/<name>` paste blocks flat and tab-completable; if a family outgrows the folder, the prefix already groups it. `./scripts/help` is the menu, read off every script's own header, and `<name> --help` prints that header. **Every header has the same layout**, the one `kubectl` and `flux` print: a one-line summary (line 2, what the menu shows), the description paragraphs (the why), then `Usage:` with one line per form, `Arguments:` and `Options:` as aligned two-column tables (`-h, --help` always last), `Environment:` where the script reads variables, `Examples:` with a comment line above each command, and `See also:` naming the rules, stages and scripts it belongs with. A new script copies that shape; the course's docs gate refuses one without the summary, `Usage:` and `Examples:`.

| `revert-gate` | Two checks. Judges whether a change drags **credentials backwards**: the one artifact whose old versions decay, since proper rotation revokes at the provider. Reads paths only (`*/secrets/*`, `*.sops.yaml`, `*.externalsecret.yaml`), never values, so it needs no key material; exits non-zero on a hit and prints the one-commit roll-forward recipe. Second check: whether the range **reverts a commit marked `!`**. If so, it prints that commit's own `Roll-forward:` trailer, which is the author's knowledge about things a path scan cannot see (a cluster that no longer exists). The path check cannot be forgotten and stays the authority. `revert-gate [base-ref] [head-ref]` | stage 20 onward: before any revert, pre-push, and as a CI check | No |
| `freeze-gate` | A customer change freeze as a **merge-time** control: reads `freezes.yaml` and fails a PR whose paths fall inside an active window. Deliberately *not* `flux suspend` on a stamp: that stops drift correction too, so the freeze window becomes the only period the cluster does not repair itself, and it never expires. Expiry here is structural (the window has an end date read from `HEAD`). `--calendar` lists active, upcoming and recently-ended windows; `--at <date>` answers "can we ship on the 20th?" before the 20th; a `Freeze-override:` trailer passes loudly and permanently, because a control that cannot be overridden gets disabled at 3am instead. `freeze-gate [--calendar] [--at <date>] [base] [head]` | stage 27 onward: the PR check, and any time someone asks what is frozen | No |
| `base-gate` | Base is sacred, as a verdict: a change under `apps/base/` or `infrastructure/base/` passes only if every root some cluster consumes on either side of it (a re-pointed stamp renders the new commit under its old path once before the binding lands; cluster roots left out) renders byte-identical on both sides, and, with `--subject`, only if the title's type is one that renders empty (`refactor`, `style`, `docs`, `chore`, a git revert). `OK` when no base tree is touched. `base-gate [--subject "<title>"] [base-ref] [head-ref]` | Stage 21 onward: the `base-gate` CI check (required), the pre-push hook, and before opening any PR that touches base | No |

Reports; blocking is branch protection's job. `path-gate [base-ref] [head-ref]` | stage 21 onward: before pushing, and as the PR check | No |

| `style-gate` | The YAML style convention as a verdict: `layout-gate` first (rules 3.1 and 3.2), then the style in two halves: **kustofmt** (the installed binary, refused unless it is the pin in `clusters/versions.yaml`; the format authority, kyaml's own emitted style; skips sops files itself) then **yamllint** with the committed `.yamllint.yaml` (what formatting can't express). `flux-system/` (tool-owned, `flux install --export` output) is dropped from any list it is handed, named when the list was explicit. `style-gate [files...]`; no args = every tracked YAML | stage 11 onward: paste block, CI style job, pre-commit (changed files) and pre-push hooks | No |
| `commit-gate` | The [commit convention](https://github.com/blairforce1/gitops-golden-path-course/blob/main/appendices/commit-convention.md) as a verdict, one grammar, four ways in: `--range <rev-range>` judges real commits, `--file <path>` is the `commit-msg` hook's argument, `--subject "<text>" ["<body>"]` is the PR-title check (with `merge_commit_title=PR_TITLE`, that string becomes a commit on `main`), and **`--docs` extracts every `git commit -m`, `--title` and `--commit-template` string from the walkthrough and judges it identically**, so the course cannot teach a convention it has stopped following. Scope registry enforced only for the domain types, which is where the two commit populations divide; a `!` subject must carry a `Roll-forward:` trailer, checked wherever a body exists (a bare PR title has none, and says so rather than passing quietly) | stage 11 onward: `commit-msg` hook, pre-push, CI, and the PR check | No |
| `style-fix` | Formats YAML in place with kustofmt (the installed binary, refused unless it is the pin): `-l` lists what differs, `-w` rewrites exactly that list, so the output names each file touched. sops-encrypted and unparseable files are never listed, so never rewritten | When `style-gate` reports format failures | Rewrites tracked YAML in place (formatting only; renders are unaffected) |
| `rung-time` | Lead time for one ladder rung, measured honestly: waits for the cluster to report it applied *that* revision and for the rollout to finish, then reads the status that says `reconciliation succeeded`. Without both, the first green on the commit (Flux posts every non-error event as success, `dependency not ready` included) makes a 35s promotion look like 4s. `rung-time <sha-or-subject> <status-context> <kube-context> <stamp>`; works live or after the fact | The Act II and III checkpoints' drill 2; any time you want a defensible lead-time number | No |
| `commit-by-subject` | The sha of the commit whose subject is exactly the one given: first-parent (the merge, never the branch commit that shares its title), awk not `--grep` (a substring search finds the revert that quotes the subject; no `grep.patternType` can reinterpret the grammar's parentheses), GitHub's ` (#N)` suffix ignored unless the subject you give carries one. `--prefix` for a grammar-derived stem such as `break(app-prod): `. `rung-time`, `detect-time`, `evidence`, `revert-gate` and `act-1-drill` all resolve commits through it | The checkpoints' drills 2 to 4; anywhere a commit is named by what it did rather than by `HEAD` | No |
| `detect-time` | How long from a break landing in git to the fleet view knowing: read off `gotk_resource_info` on the hub, with the stamp's Ready-state timeline either side of the break so the number shows its working. In a drill the break is labelled, so it finds it by the **`break(<stamp>): ` subject prefix** derived from the stamp name, the commit convention's payoff, and the third argument is only needed to disambiguate several breaks against one stamp. Prefix-anchored on purpose: `git revert` writes `Revert "<subject>"`, so a substring search finds the revert (newer, and the opposite event) while a prefix match cannot. A real break is never labelled - a feat, a pin, a promote that hurt - and is found the other way round, from the failed revision the stamp's `status.history` names: pass that sha as the third argument. A hub whose history begins after the break (a rebuilt hub starts empty) is named as such, not as a missing series: the numbers then live only in the record made before the rebuild. `detect-time <stamp> <kube-context> [break-commit-subject \| sha] [window]` | The Act III checkpoint's drill 3; any time you want a defensible detection number | No |
| `evidence` | The auditor's dossier for one commit, from durable artifacts only: the change and its author, who touched those paths afterwards, the **full status sequence** (the plural `/statuses` endpoint, so the ordering shows: `/status` is latest-per-context and hides it), what the cluster actually applied, and a plain-English closing paragraph. Derives the stamp and cluster from whichever status context went red, so nothing has to be told where to look. `evidence <sha|subject-prefix> [stamp] [kube-context]` | The Act II and III checkpoints' drill 4; any incident review where the question is what shipped and who knew | No |
| `release-notes` | Release notes for **one cluster**, from what that cluster says it is running: `.status.lastAppliedRevision` is the range's far end, so no tag, release branch or changelog file has to be kept honest. Filters to the paths that render to that stamp (read from its `.spec.path`) and groups by the commit grammar via pinned git-cliff. `release-notes <stamp> <kube-context> [since] [--first-parent] [--record]`; `since` accepts `<stamp>@<kube-context>` to compute the **promotion gap** between two rungs | stage 26 onward; before any promotion, to see what is waiting | No (`--record` writes `.release-notes/`) |
| `dora` | The four DORA metrics from artifacts, **scoped to production**: the last rung of the ladder. The **unit is the change, not its application**; **lead time ends at the first production arrival**, because it measures the feedback loop. Its clock starts at the commit the *production stamp applied*, i.e. the **promotion**, not the dev commit, so **`--stages`** decomposes what that hides: `dev→PR` (soak or queue), **`review`** (PR opened→merged, from `gh`), `merge→prod`. The join across those commits is the version token the [commit convention](https://github.com/blairforce1/gitops-golden-path-course/blob/main/appendices/commit-convention.md) puts in `pin(app-dev): app <V>` and `promote(app-prod): app <V>`. Books each production application against the first revision the stamp reports after it, bounded by the next application (under `wait: true` the generation moves at the apply and the revision after the health check, so a sample between them must not credit the predecessor); a rollout the stamp never reports as applied is an application, not a change, and the report names it on a `refused` line. Warns when Prometheus retention is shorter than `--window` and recomputes rates over the span actually covered. `dora [--window 30d] [--production <regex>] [--by tenant\|cluster\|stamp] [--rungs] [--stages]` | stage 10 onward | No |
| `refresh-hub-address` | **Fallback for environments that don't resolve container names.** `cluster-facts` normally name the hub by the platform node's container name, which survives reboots and rebuilds; a pinned IP dies with the node container, so this re-derives it into every cluster's `cluster-facts` ConfigMap. | `slo-watch` | Prints one line per sample of a cluster's SLIs, availability, p95, whether the burn alert is firing, so the *time* dimension is visible: a break takes ~1–3 minutes to show in a 5m rate window, a fix takes the window length to clear. `slo-watch <cluster> [interval]`; Ctrl-C to stop | Stage 09's drill, either side of a deliberate break; any time you want to see an SLI move | No |
| `slo-gate` | The promotion ladder's second signature: asks the hub whether a rung met its SLO over a soak window, availability vs target, p95 latency, no burning alerts; **no traffic is a FAIL** (absence of evidence is not health). `slo-gate <cluster> [window]`. Also refuses a candidate the rung has not applied yet (the stamp's revision on the hub must match what git says `main` is: between a merge and the end of its rollout the rung still runs the predecessor) and one younger than `SLO_MIN_SOAK` (default 2m): residency is read from when that revision first appeared in `gotk_resource_info`, so two quick merges cannot pass on the predecessor's health - a production ladder sets it to the full window. The target is **read from the SLO in git** (`slo:app_availability:target`), so the promise has one home; `SLO_TARGET`/`SLO_P95_MAX`/`SLO_MIN_SOAK`/`SLO_STAMP` override for what-if runs | Before any prod promotion (stage 09 onward); the act checkpoint's rung-2 gate | No |
| `soak-gate` | The soak per ascent as a gate: reads `soak.yaml` (artifact kind x target rung) and holds every promotion pointer a change moves to it, the time served read from the first-parent commits that put the candidate on the rung above and kept it there (rule 5.8); a rung skipped is a FAIL, not a soak. A `Soak-waived:` trailer passes it loudly, in the record. `<kind> <rung>` judges one ascent before the change exists; `--declared` prints the table; `--due` is `check-ladder-due`, and `--due --items` opens a work item per due ascent | Every push (the pre-push hook) and every PR (CI's `pr-record`) from stage 16; by hand before a promotion, and in the `promote` skill | No |
| `check-ladder-due` | What the ladder owes: one line per ascent where a rung is ahead of the one below, judged against `soak.yaml`'s `min` and `max` from git's dates: SOAKING, DUE, FAIL past `max`, FROZEN when the calendar covers the rung's paths, HELD when the ascent's item was closed with a reason (a decision not to promote). `soak-gate --due` under a `check-*` name, so `./scripts/check` runs it | Every stage start through `check`; daily on a fleet (stage 27 wires the schedule) | No |

## Contracts

- **Checkpoints** print one `PASS`/`FAIL` line per check with what it means, and exit non-zero on any failure: bare unlabeled output is banned at gates. CI runs the identical files, so local and CI verdicts can't diverge.
- **Destructive scripts** demand an explicit flag and print exactly what they will destroy when run without it.
