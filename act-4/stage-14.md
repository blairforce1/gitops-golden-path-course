# Stage 14 - Image automation (the robot on the dev rung)

[← 13 - Platform promotion (change the ingress version)](stage-13.md) · [Walkthrough index](../README.md)

> **Where you are:** the root of the config repo, on `main`. **Starting state:** 13 complete and the fleet live. If it isn't, the previous act's `act-3-drill` rebuilds it from git (git is at HEAD, so everything since comes back with it). **Why here:** it pairs with stage 12 so the robot's commits carry rendered diffs. No overlap with stage 13: Renovate owns *platform* currency (charts, flux itself); this owns *app image* pins.

**Goal:** stage 07 taught the human workflow: new image, dev pin by commit, prod pin by PR. (The robot built here **polls** the registry on an interval; [stage 15](stage-15.md) removes that wait by having the build announce itself, without removing the poll that guarantees it.) This quest hires a robot for the first half: Flux's image automation watches the registry, and when a new app image appears it **opens a PR moving the dev pin, which merges itself when the required checks pass**, then stops. And because from here a robot writes the pin and a human only reads it, the pin changes shape: the robot writes the image's **digest** beside its tag, the promotion carries that digest to prod, and stage 08's policy gate holds every rung to it, so that a pin names an artifact and not a label. The design sentence up front: **the robot gets exactly the human's dev privileges and not one more.** The human's dev privilege, since stage 02, is *open a PR to `main` and merge it on green without a second reviewer*. So that is what the robot gets: a branch to write to, the repository's own token to open the PR, and auto-merge on the same required check a human waits for. The ruleset from stage 00 keeps its zero bypass actors; prod stays a human PR on dev's evidence; and every principal in the chain is a robot you can name ([rule 1.3](../rules.md#13-protection-from-day-zero-nothing-reaches-main-except-a-merged-pr)).

> **The rule that trips people, stated plainly: version automation applies to DEV, and only dev.** No other environment ever receives an automated version bump. New versions *enter* the ladder automatically; they *climb* it only by deliberate, reviewed PR. That's not the automation being half-installed. It's the promotion discipline applied to robots, and it's why the prod overlay never gets a setter marker. If you ever find yourself wiring automation at prod "to save the PR step," you've deleted the ladder, not automated it. One subtlety in *this* fleet: the platform cluster runs the **dev overlay** (its `app-dev` stamp, a *stamp* being a Flux `Kustomization` CR), so platform receives automated bumps transitively, at the same instant dev does. That is **by design, and it stays**. The instinct to give platform its own app pin ("it tests *next* for Kubernetes, shouldn't it lead for apps too?") mixes up two ladders. Platform's "tests next" role belongs to the *platform's own* ladder, where it genuinely leads: Kubernetes minors ([stage 16](stage-16.md)), controllers and charts ([stage 13](stage-13.md)). For tenant apps, platform just needs *a* representative workload running to validate platform changes against, not an earlier view of app releases; a platform-specific app pin would buy symmetry and cost a third pin to move on every release, with nobody whose job is to read it. So the fleet has **two ladders with two entry points, apps entering at dev and platform changes at platform**, and each robot writes at its own ladder's entry rung, nowhere else.

## Steps

### 1. Two more controllers, and an honest credential decision

Image automation is two controllers `flux install` doesn't include by default, and a git credential that can *write*, which the cluster's deploy key can't. The controllers are a change to the platform cluster's own definition, so they arrive the way stage 03 said they would: regenerate the components file, merge it, let the cluster sync itself:

```sh
source ./env.sh
flux install --export --components-extra=image-reflector-controller,image-automation-controller \
  > clusters/platform/local-01/flux-system/gotk-components.yaml
git add clusters/platform/local-01/flux-system
./scripts/pr-open feat/18/image-controllers "feat(flux-system): image reflector and automation controllers on local-01" <<'EOF'
## What is moving
local-01's Flux components gain image-reflector-controller and image-automation-controller.

## Why now
The dev rung gets a robot; these are its hands.

## Evidence
gotk-components.yaml regenerated by the pinned CLI; the diff is two Deployments and their CRDs, nothing removed.

## If it is wrong
Revert this merge; the sync removes the controllers again.

Refs: #18
EOF
```

Read it; when the diff is what the body claims:

```sh
gh pr checks --watch --fail-fast \
&& gh pr merge --merge --delete-branch \
&& git switch main \
&& git pull
flux reconcile kustomization flux-system --with-source --context kind-ggp-local-01
flux check --context kind-ggp-local-01        # two more controllers, installed from git
```

Now the credential. The cluster's deploy key is read-only, which has been correct since stage 03; the robot needs to *push*. Mint a new key with write access and register it in the old one's place, using the same script every rebuild runs, with the one flag that names the widening:

```sh
./scripts/cluster-sync clusters/platform/local-01 --context kind-ggp-local-01 --write
```

```text

== deploy key 'flux local-01' (READ-WRITE)
✚ deploy key: ecdsa-sha2-nistp384 <public key>

► git secret 'flux-system' created in 'flux-system' namespace
   replaced the previous 'flux local-01' key (#<id>) - a rebuilt cluster is a new identity
   registered: flux local-01  read_only: false
== sync clusters/platform/local-01 (already applied from git - reconciling with the new key)
► annotating GitRepository flux-system in flux-system namespace
✔ GitRepository annotated
◎ waiting for GitRepository reconciliation
✔ fetched revision main@sha1:<sha>
► annotating Kustomization flux-system in flux-system namespace
✔ Kustomization annotated
◎ waiting for Kustomization reconciliation

```

Then the stamp table, every row Ready. The first line is the script telling the truth about a live cluster: the CLI refuses to install over a Flux that syncs itself, and there is nothing to install, because step 1's merge already put the two controllers there; the sync pair is likewise already on the cluster from git, so the script reconciles rather than applying over Flux's own objects. The fetched revision is the proof the new key works: source-controller cloned `main` with it. Name what just changed before moving on: the platform cluster's repo credential went from read-only to **read-write**, a real widening, scoped to one deploy key on one repo, held by the cluster designated to absorb risk. That's the entire write path the robot has, and `main` is not on it: the ruleset refuses a direct push from this key exactly as it refuses one from you. The robot's write path is a *branch*; everything from there is a PR.

Two placements, kept apart on purpose. The robot *writes* at dev, the ladder's entry rung for app images, and *runs* on platform, the cluster the fleet's singletons live on (the monitoring hub has since Act III). A rung is a replica: dev-01 is rebuilt without ceremony and could be one of several, and a second dev cluster would be a second robot pushing the same branch; a write credential also belongs on the cluster designated to absorb risk, not on one running tenant workloads. The cost is that platform is the fleet's most volatile cluster, first to take a Kubernetes minor or a chart bump, and when it is down or being rebuilt the robot is down with it. What that costs dev is the automation, not the deploy: dev-01 keeps syncing `main`, and the dev pin moves the way it has since stage 07, by a human PR on the same line, until `cluster-sync --write` on the rebuilt platform brings the robot back and its first scan opens one PR to the newest tag ([stage 16](stage-16.md) rehearses exactly this).

### 2. What to watch, and what counts as newer

An `ImageRepository` scans the registry; an `ImagePolicy` defines "newest." Both are binding resources of the platform cluster, committed CRs like everything else it runs:

```sh
flux create image repository app \
  --image=$APP_IMAGE --interval=5m \
  --export > clusters/platform/local-01/resources/app.imagerepository.yaml
flux create image policy app \
  --image-ref=app --filter-regex='^\d+\.\d+\.\d+-run(?P<ts>\d+)$' --filter-extract='$ts' --select-numeric=asc \
  --reflect-digest=IfNotPresent \
  --export > clusters/platform/local-01/resources/app.imagepolicy.yaml
```

Read the policy, because it is the line that must match the tag scheme, and a semver range does not match this one. The app's dated tags (`0.1.1-run20260812163232`) are builds of 0.1.1 that semver's grammar files as **prereleases** of it, and the registry has held a clean `0.1.1` since Act I's checkpoint. A release outranks its own prereleases, so a range such as `>=0.1.0-0` (the `-0` opts prereleases in) resolves "newest" to the Act I image, older than the pin every rung runs, and the robot's first act would be to propose that downgrade. The scheme is build-dated, and the policy Flux documents for a build-dated scheme is the date: `filterTags` keeps the tags of that shape and extracts the timestamp, the numerical policy orders on it, and `asc` selects the last. That is a borrowed correctness with an expiry date, and it's worth saying so: the day the app mints clean semver (`v0.1.2`), the filter does not match it, the policy sits on the last dated build without a word, and this file changes to `--select-semver=">=0.1.0"` with the scheme. That is the point of the file: it is the one place that encodes what "newer" means, and a tag scheme that changes shape changes it.

Read the other flag too, because it is the one this stage is really about. A tag is a label the registry lets anyone move; a digest is the content's hash and cannot be moved. `--reflect-digest=IfNotPresent` makes the policy record, when a tag first wins, the digest the registry served for it (`status.latestRef.digest`) and never read it again: the honest setting for release tags, which are supposed to be immutable and which no registry can promise are. `Always` re-reads on every scan and exists for tags such as `latest`, which stage 08 banned; `Never` is the old behaviour, a tag and a hope. From here the robot knows two things about every release, and step 3 lets it write both.

### 3. Mark the lines the robot may edit

The automation edits only fields carrying a **setter marker**, an exact-match comment naming the policy and the field. The dev pin gets two: the tag, and a digest field it does not have yet. Give it one first, from the cluster's own word on what it is running, since a pod's `imageID` is the digest the node actually pulled (`yq` writes the comments, and because this file carries lists, `style-fix` follows it, as [rule 3.5](../rules.md#35-the-tool-writes-the-file) requires; the markers survive the formatter byte for byte):

```sh
source ./env.sh
tag=$(yq '.images[0].newTag' apps/overlays/dev/kustomization.yaml)
digest=$(kubectl --context kind-ggp-dev-01 -n ggp get pod -l app.kubernetes.io/name=app \
  -o jsonpath='{.items[0].status.containerStatuses[0].imageID}'); digest=${digest##*@}
(cd apps/overlays/dev && kustomize edit set image $APP_IMAGE:$tag@$digest)
yq -i '.images[0].newTag line_comment = "{\"$imagepolicy\": \"flux-system:app:tag\"}" |
       .images[0].digest line_comment = "{\"$imagepolicy\": \"flux-system:app:digest\"}"' \
  apps/overlays/dev/kustomization.yaml
# yq re-indents every list; kustofmt puts them back, comments intact
./scripts/style-fix apps/overlays/dev/kustomization.yaml
git diff apps/overlays/dev/kustomization.yaml    # one new field, two comments
kustomize build apps/overlays/dev | grep 'image:'  # → ghcr.io/…/app:<tag>@sha256:<digest>
```

Read the render: the image reference now carries both names. The kubelet pulls by the digest and ignores the tag, which stays for the humans reading the file; the bytes are the ones dev is already running, now named in git the way the cluster names them. It is still a change to what the rung renders, so it is a PR like any other, with the markers riding along:

```sh
git add apps/overlays/dev
./scripts/pr-open pin/18/dev-by-digest "pin(app-dev): app $tag by digest" <<EOF
## What is moving
Dev's pin gains the digest of the image it is already running (${digest:0:19}…), and both fields carry the robot's setter marker.

## Why now
A robot is about to write this pin. A human reads a tag; a cluster and an auditor need the digest.

## Evidence
The digest is dev-01's running pod's imageID; the render changes only the image reference.

## If it is wrong
Revert this merge; the rung re-pulls the same bytes by tag.

Refs: #18
EOF
```

Read it; when the diff is what the body claims:

```sh
gh pr checks --watch --fail-fast \
&& gh pr merge --merge --delete-branch \
&& git switch main \
&& git pull
```

Note the shape of the permission model: the robot holds a repo-wide write key, but its *edit surface* is every line someone deliberately marked, currently two, both in one pin. The prod overlay has no marker; the robot couldn't move prod's pin even if told to. That is load-bearing well beyond this stage: because *every* path to `main` is a merged PR, the robot's included, every merge-time control the course adds later is **complete** rather than partial. [stage 27](../act-6/stage-27.md)'s change freeze depends on it directly.

### 4. The automation itself - and the PR it cannot open

The robot needs a work item before it needs hands; [rule 2.5](../rules.md#25-every-change-has-a-work-item-the-trailer-is-the-reason) has no exception for it. The honest shape is a *standing* one: the automation is a running piece of work, so every pin it proposes cites the same issue, and the issue closes when the automation is retired, not when a pin moves. Create it now and keep its number, because the robot's own commit must carry the trailer: on a push to the robot's branch, stage 11's `pr-record` judges the commit message, there being no PR yet, and a commit citing nothing is a refused merge.

```sh
gh label create automation --color 0e8a16 --description "standing work items for robots" --force
n=$(gh issue create --title "Image automation: the dev pin follows the image policy" --label automation \
  --body "Standing work item for the image robot (stage 14). Every PR it opens cites this issue; it closes when the automation is retired, not when a pin moves." \
  | grep -oE '[0-9]+$')
echo "the robot's standing work item: #$n"
```

```sh
flux create image update app-dev \
  --git-repo-ref=flux-system --git-repo-path="./apps/overlays/dev" \
  --checkout-branch=main --push-branch=flux-image-updates \
  --author-name=fluxcdbot --author-email=fluxcdbot@users.noreply.github.com \
  --commit-template="pin(app-dev): app {{range .Changed.Changes}}{{if eq .Setter \"flux-system:app:tag\"}}{{.NewValue}}{{end}}{{end}}

Refs: #$n" \
  --interval=5m \
  --export > clusters/platform/local-01/resources/app-dev.imageupdateautomation.yaml
(cd clusters/platform/local-01/resources && \
 kustomize edit add resource app.imagerepository.yaml app.imagepolicy.yaml app-dev.imageupdateautomation.yaml)
```

Read the two lines that encode the design. `--checkout-branch=main --push-branch=flux-image-updates` means the robot starts from `main` and pushes to **a branch**, created from `main` if absent and overwritten from `main` plus the change if it exists, so it is never stale. It also outlives its PR: stage 00's `delete_branch_on_merge` does not fire on a merge performed by an app token, and the repository's own token is one, so after the merge the branch parks at the merged commit, an ancestor of `main`, until the next release overwrites it. `--git-repo-path` scopes its working set to the dev overlay. The commit template picks the tag setter's new value and nothing else, so the robot's subject is `pin(app-dev): app <tag>` to the character: the shape stage 10's `--stages` joins on and stage 11's `pr-record` judges; the digest moves in the same commit and shows in the diff, not the subject. The template's second paragraph is the trailer, so the commit cites the work item the way yours do, and the export renders it as a `messageTemplate` block. What Flux does not do is open the PR; nothing in the cluster holds a credential that can, and it should not. The repository can open its own PRs, with the token every workflow run is issued, once it is told it may. GitHub ships that permission off, so that no workflow opens a PR nobody decided it could; turning it on is one repository setting, and it widens nothing else (the token's default stays `read`, and the workflow below names the two permissions it needs):

```sh
gh api -X PUT repos/{owner}/{repo}/actions/permissions/workflow -F can_approve_pull_request_reviews=true
gh api repos/{owner}/{repo}/actions/permissions/workflow
```

```text
{"default_workflow_permissions":"read","can_approve_pull_request_reviews":true}
```

So the second half of the robot is a workflow, triggered by the robot's push, which reads the work item back off the commit rather than keeping a second copy of the number:

```sh
cat > .github/workflows/image-update-pr.yaml <<'EOF'
name: image-update-pr
on:
  push:
    branches:
    - flux-image-updates
permissions:
  contents: write
  pull-requests: write
jobs:
  open-and-arm:
    runs-on: ubuntu-latest
    steps:
    - uses: actions/checkout@v4
      with:
        fetch-depth: 0
    - name: open the PR (or refresh it), then arm auto-merge
      env:
        GH_TOKEN: ${{ secrets.GITHUB_TOKEN }}
      run: |
        subject=$(git log -1 --format=%s)
        moved=$(git diff --stat origin/main...HEAD | tail -1)
        # the standing work item, read off the robot's own commit (its template carries the trailer)
        issue=$(git log -1 --format=%B | grep -oE '^Refs: #[0-9]+' | grep -oE '[0-9]+')
        body="## What is moving
        The dev pin, moved by image automation: $moved

        ## Why now
        A newer image matched ImagePolicy flux-system/app.

        ## Evidence
        Auto-merges when the required checks pass; the fleet reports per cluster on the merge commit.

        ## If it is wrong
        Revert the merge (scripts/pr-revert); the robot only ever proposes a newer tag and its digest.

        Refs: #$issue"
        if [ -z "$(gh pr list --head flux-image-updates --state open --json number --jq '.[0].number')" ]; then
          gh pr create --base main --head flux-image-updates --title "$subject" --body "$body"
        else
          # a newer tag arrived before the last PR merged
          gh pr edit flux-image-updates --title "$subject" --body "$body"
        fi
        # arm auto-merge; a forge without it (free plan, private repo): wait for the checks, then merge
        gh pr merge flux-image-updates --auto --merge \
          || { gh pr checks flux-image-updates --watch --fail-fast && gh pr merge flux-image-updates --merge; }
EOF
yq -i '.on.push.branches += ["flux-image-updates"]' .github/workflows/verify.yaml
./scripts/style-fix .github/workflows/verify.yaml   # yq re-indents the lists; then the diff is one line
```

The `yq` line is the one that makes it work, and it deserves its own paragraph. (`contents: write` on the workflow is what lets the repository's own token arm auto-merge and, on a forge without it, merge; the token still cannot push to `main` past the ruleset.) A PR opened with `GITHUB_TOKEN` gets **no working** `pull_request` run: GitHub's rule against workflows triggering workflows records the event and fails it before a job is scheduled, so beside every robot PR sit a `verify` and a `rendered-diff` run that are red with zero jobs, and no rendered-diff comment ever appears. Left there, the checks the ruleset requires would never report on the robot's PR, and auto-merge would wait forever. Stage 08 said the `push` trigger would matter for a reason not yet visible: this is it. `verify` now also runs on pushes to the robot's branch, its check reports against the branch's head commit, and that is what a required check reads, whichever event produced it. The alternative, a personal or app token so `pull_request` fires, is a secret, and therefore an IOU; the course does not take it. The last line's fallback is for a forge with no auto-merge (a free-plan private repo): the workflow waits for the checks itself and merges on green, so the robot still never lands an unchecked change; it merely stops being the ruleset's job to guarantee it.

```sh
git add clusters/platform/local-01 .github/workflows
./scripts/pr-open feat/18/image-automation "feat(app-dev): image automation - robot proposes the dev pin by PR, humans keep prod" <<'EOF'
## What is moving
ImageRepository, ImagePolicy and ImageUpdateAutomation on local-01 (push branch flux-image-updates); a workflow that turns that branch into a PR and arms auto-merge; verify now checks pushes to that branch.

## Why now
New app versions should enter the ladder without a human, and climb it only with one.

## Evidence
The automation's edit surface is one marked line in the dev overlay; the workflow holds no secret; the ruleset is unchanged and has no bypass actors.

## If it is wrong
Revert this merge; the controllers stay, the automation and the workflow go.

Refs: #18
EOF
```

Read it; when the diff is what the body claims:

```sh
gh pr checks --watch --fail-fast \
&& gh pr merge --merge --delete-branch \
&& git switch main \
&& git pull
flux reconcile kustomization flux-system --with-source --context kind-ggp-local-01
```

Gate: the machinery reports before any release exists:

```sh
flux get images all --context kind-ggp-local-01
```

Expected: the repository `successful scan: found <n> tags`; the policy `resolved to <tag> with digest sha256:<digest>`; the automation `repository up-to-date`, its last run the policy's scan time. Read the policy row against the dev overlay's pin (`yq '.images[0]' apps/overlays/dev/kustomization.yaml`): the same tag and the same digest is the robot agreeing with the humans about the present, a good sign before trusting it with the future. Any other tag there is the policy and the tag scheme disagreeing (step 2), and the robot has already pushed the disagreement to its branch; the troubleshooting table has the recovery, and its order matters: policy first, branch second.

### 5. Mint a release and don't touch anything

The stage-07/act-checkpoint release dance, minus every step after the tag. That's the point:

```sh
source ./env.sh
cd "$APP_DIR" && git pull
TAG="v0.1.1-run$(date +%Y%m%d%H%M%S)"
git tag "$TAG" && git push origin "$TAG"
echo -n "waiting for the registry to have ${TAG#v} (multi-arch build, ~2-3m) "
until docker manifest inspect $APP_IMAGE:${TAG#v} >/dev/null 2>&1; do printf .; sleep 10; done; echo
cd -
```

Gate: within the scan+automation intervals (≤10m) a PR opens that you didn't write; within one CI run more it merges itself, and the fleet treats the merge like any other: statuses land per cluster, dev clusters roll:

```sh
gh pr list --state all --limit 1 --json number,title,author,state --jq '.[] | "#\(.number)  \(.state)  \(.title)  opened by \(.author.login)"'
n=$(gh pr list --state merged --limit 1 --json number --jq '.[0].number')
gh pr view $n --json mergedBy,mergeCommit --jq '"#'$n' merged by \(.mergedBy.login)  merge commit \(.mergeCommit.oid[0:7])"'
git pull \
&& git log -1 --format='%h  %an  %s' \
&& git log -1 --format='%h  %an <%ae>  %s' HEAD^2
gh api "repos/{owner}/{repo}/commits/$(git rev-parse HEAD)/status" \
  --jq '.statuses[] | .context + "  " + .state'
```

Read the principals, because this is the property the design was chosen for: the pin commit (the merge's second parent) is authored by `fluxcdbot` and was pushed with the deploy key named `flux local-01`; the PR was opened and merged by `github-actions[bot]`; the merge commit's subject is the robot's subject, because the workflow used it as the title. Stage 11's `pr-record` check judged that subject, and the `Refs:` trailer naming the standing automation issue, on the push to `flux-image-updates` before auto-merge could fire; it passes because step 4's `--commit-template` is written to the grammar and carries the trailer, and the workflow copies that trailer into the PR body. The robot clears the same checks you do, or it waits. One thing its merge does not do is run `verify` on `main`: a push performed with the repository's token raises no workflow, the rule step 4 already paid for, so the checks on record for this merge are the branch head's, and the fleet's statuses on the merge commit are its evidence. **Your name appears nowhere.** The change record says a robot proposed it and a robot landed it, on a check a human would have had to pass too. The pin it moved carries the marker it obeyed: attribution, mechanism, and permission all readable from git.

Read the pin it moved, too. Git, the policy and the registry should name one artifact:

```sh
source ./env.sh
git show HEAD^2 --format= -- apps/overlays/dev | grep -E '^[-+]( |- )'
kubectl --context kind-ggp-local-01 -n flux-system get imagepolicy app -o jsonpath='{.status.latestRef.tag}@{.status.latestRef.digest}{"\n"}'
tag=$(yq '.images[0].newTag' apps/overlays/dev/kustomization.yaml)
gh api /user/packages/container/$APP_REPO/versions --jq ".[] | select(.metadata.container.tags[] == \"$tag\") | .name"
```

```text
-- digest: sha256:<old digest> # {"$imagepolicy": "flux-system:app:digest"}
+- digest: sha256:<new digest> # {"$imagepolicy": "flux-system:app:digest"}
-  newTag: <old tag> # {"$imagepolicy": "flux-system:app:tag"}
+  newTag: <new tag> # {"$imagepolicy": "flux-system:app:tag"}
<new tag>@sha256:<new digest>
sha256:<new digest>
```

Two lines moved in git, the tag and the digest. The policy's latest ref is the same pair, the digest being the one it reflected when the tag first won. The registry's version for that tag has the same digest as its name. Three registers, one artifact. Prod, meanwhile, hasn't moved: promoting this release is still your PR, on this merge's green evidence, and it is the next step, because the promotion is where the digest earns its keep.

> One refinement a real fleet makes and this course does not: a dedicated GitHub App for the robot, so `mergedBy` reads `platform-bot` rather than the generic Actions identity. It is a second app registration and a secret, an IOU this course declines to take on a kind cluster.

### 6. Promote what dev ran, by digest

Stage 09 named a gap: `slo-gate` certifies the *revision* dev applied, and a promotion moves a *tag*, two names joined by nothing but convention. The digest closes it. Promote as at stage 09, both signatures, with the pin copied from dev's overlay and checked against the pod dev is running before anything is written.

**First, traffic.** The gate reads dev's error budget over a window, and an SLO over zero requests is no evidence at all. Start the probe in **its own terminal** and leave it running until the promotion merges (Ctrl-C then):

```sh
curl -s -X PUT -d 'stage 14 probe' http://localhost:8081/notes/slo
while true; do curl -s -o /dev/null http://localhost:8081/notes/slo; sleep 0.5; done
```

Give it a few minutes before the gate, or `slo-gate` correctly refuses on `traffic over 10m: NONE`. The robot's merge is recent too, so a gate run straight away meets `candidate soaked NNs of the 2m required`, stage 09 step 9's residency check. Both are the gate working; wait them out and re-run. Then the pin dev runs against the pin dev's overlay names, and the gate:

```sh
source ./env.sh
tag=$(yq '.images[0].newTag' apps/overlays/dev/kustomization.yaml)
digest=$(yq '.images[0].digest' apps/overlays/dev/kustomization.yaml)
running=$(kubectl --context kind-ggp-dev-01 -n ggp get pod -l app.kubernetes.io/name=app \
  -o jsonpath='{.items[0].status.containerStatuses[0].imageID}'); running=${running##*@}
[ "$running" = "$digest" ] && echo "dev runs $digest" || echo "dev is not on the overlay's digest yet: wait for the rollout"
./scripts/slo-gate dev-01 10m
```

```sh
(cd apps/overlays/prod && kustomize edit set image $APP_IMAGE:$tag@$digest)
git add apps/overlays/prod
```

### 7. The gate holds every rung to it

Discipline in step 6, enforcement now, on the rails stage 08 built: a rule over rendered output, in the same `policy/` the workload baseline lives in, so the one gate refuses a tag-only pin in the paste block, in CI, and (stage 11) at the pre-push hook. ```sh

```sh
package main

# From stage 14 a pin names an artifact, not a label: every app image a render carries

EOF
```

## Troubleshooting

| Symptom | Likely cause | Fix |
|---|---|---|
| Automation Ready but no commit ever appears | Marker string inexact; it's matched literally, namespace:name:field included | Step 3's `yq` line, verbatim: `{"$imagepolicy": "flux-system:app:tag"}` on the tag, `…:app:digest` on the digest |
| The robot's PR moves `newTag` but not `digest` | The `:digest` marker is missing, or the policy's digest reflection is `Never` | Step 3's second comment; step 2's `--reflect-digest`; `flux get image policy app` must show a digest in the latest ref |
| The robot's subject ends at `app` with no version | The template's setter name does not match the marker, so the `if` never fires | Step 4's template names `flux-system:app:tag` verbatim; the automation's status shows the message it rendered |
| `policy-gate` red: `pinned by tag only` on prod | Prod's pin predates step 6 | Promote by digest (step 6) before the rule lands; the rule is last for exactly this reason |
| `checkpoint-07` red on `runs the overlay's pin` after step 3 | A checkpoint older than digest pins read the tag as everything after the last colon | `tools/sync-seed` from the course: the current one reads the tag before `@` and holds the cluster to the digest after it |
| `push: permission denied` in the automation's status | Deploy key still read-only (`cluster-sync` run without `--write`) | Step 1's second block; confirm at GitHub → repo settings → deploy keys (`flux local-01` shows write access) |
| The PR opens but never merges | `verify` did not run on the branch (the `push` trigger edit in step 4), or auto-merge is off in repo settings (stage 00's `allow_auto_merge`) | `gh pr checks <n>`: no checks means no trigger; `gh api repos/{owner}/{repo} --jq .allow_auto_merge` must be `true` (free plan, private repo: it cannot be; the workflow's fallback waits and merges instead; check its run log) |
| The PR opens, `pr-record` is red, nothing merges | Step 4's `--commit-template` drifted from the grammar, the robot's subject being its PR's title, or the standing `automation` issue is closed or missing, so the body says `Refs: #` and cites nothing | Fix the template's `pin(app-dev): …` shape by PR; reopen or recreate the standing issue (step 4). The robot's next commit re-edits the PR and the check re-runs |
| `gh pr checks --watch` ends at once with `no checks reported on the '…' branch` | It ran before the push's first check registered (a script chaining it straight after `pr-open`) | Run it again; and never inside an `&&` chain under `set -e`, which does not stop on a failure there |
| The policy resolves a clean tag (`0.1.1`) over the dev pin, and the robot's first commit is a downgrade | A semver range: a release outranks its own prereleases, and the dated tags are prereleases of `0.1.1` by semver's grammar | Step 2's filter and numerical policy, by PR, and wait until the policy resolves the pin; only then delete the robot's branch (`git push origin --delete flux-image-updates`), which it recreates only from a real difference |
| `image-update-pr` fails at `gh pr create`: `GitHub Actions is not permitted to create or approve pull requests` | The repository setting is off (GitHub's default) | Step 4's `gh api` line; then `gh run rerun <id>` on the failed run, or wait for the robot's next push |
| Robot commit red on `app-dev` contexts | The image is newer than the *clusters* can pull (GHCR publish race), or genuinely broken | Same triage as any dev commit; the robot changed who typed, not how failures behave |
| The PR opens, `pr-record` is red on the branch with `no Closes:/Refs: trailer`, nothing merges | The automation's commit template lacks the trailer; on a push there is no PR body to judge, only the commit | Step 4's template, both paragraphs; the automation's status shows the message it rendered |
| The workflow opens the PR but `gh pr merge --auto` fails with a permission error | The workflow's `permissions:` lack `contents: write`, which arming auto-merge and merging need | Step 4's workflow header, verbatim |
| Two red `pull_request` runs beside every robot PR, zero jobs each, and no rendered-diff comment | GitHub records and refuses the event a token-opened PR raises | Nothing to fix: the checks of record are the push run's; read `gh pr checks`, not the runs list. The robot's diff is two lines and the PR body names them |
| Two robots fight (Renovate touches the same line) | Renovate's fence widened beyond stage 13's `managerFilePatterns` | Renovate owns `infrastructure/base/` and the platform overlay; image pins are this stage's; keep the fence and the `ignorePaths` |
